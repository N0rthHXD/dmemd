# 容量与性能验收规格

状态：T1.4 规格已固定；P7 T7.5 尚未执行。本文所有数值是**项目补充验收目标**，不是原架构
承诺的 SLA，也不作为 P1–P6 的完成门禁。只有按本规格实际运行并保留原始结果后，才能声明
性能验收通过。

## 1. 参考测试环境

| 项目 | 固定值 |
| --- | --- |
| 操作系统 | Linux x86_64（内核与发行版随 P7 报告记录） |
| CPU | 8 vCPU，无容器 CPU quota，允许使用全部 8 个逻辑核 |
| 内存 | 16 GiB |
| 存储 | 本地 NVMe SSD，ext4；数据库、WAL 与结果目录同盘 |
| Go | `.go-version` 固定的 `1.27.3` |
| SQLite | `modernc.org/sqlite v1.60.1` 内置 `3.53.4` |
| 构建 | `CGO_ENABLED=0`，`-trimpath` |
| 服务 | 单进程、单 Worker、默认 `busy_timeout=5s`、读池 4 连接 |
| 网络 | 回环 HTTP/1.1，客户端与服务同机 |

P7 报告必须记录实际机器型号、CPU 型号、内存、文件系统与 Go/SQLite 版本。机器不同不能
直接套用结果，必须重新测量或明确标注为“不同环境参考”。

## 2. 数据生成规则

### 2.1 容量口径

“十万条有效记忆”指 `state=active` 的记忆恰好 100,000 条。另生成：

| 数据 | 数量 |
| --- | --- |
| active 记忆 | 100,000 |
| archived 记忆 | 20,000 |
| deleted 记忆（仅保留墓碑与历史） | 5,000 |
| sources | 120,000 |
| evidence | 250,000 |
| memory revisions | 约 135,000 |
| 搜索索引中的文档 | active + archived = 120,000；deleted 不进入索引 |

版本分布：70% 记忆 1 个版本，20% 2 个版本，8% 3 个版本，2% 4–6 个版本。证据分布：
每个版本 1–3 条，平均约 1.8 条；其中 80% 可定位到来源片段，20% 只保留来源关联。

### 2.2 文本与词分布

固定随机种子 `20261020`，生成器必须可重复。文本长度：

| 长度（Unicode 字符） | 占比 |
| --- | --- |
| 标题 4–24 | 全部 |
| 正文 10–30 | 20% |
| 正文 31–150 | 60% |
| 正文 151–400 | 20% |

语言分布：55% 中文、25% 英文、20% 中英文混合。词表使用确定性的 Zipf 分布：

- 12,000 个常见中文词/字组、8,000 个常见英文词；
- 20,000 个稀有词（中文/英文各半），每个稀有词只出现在少量文档中；
- 保留 200 个只出现一次的极稀有词，用于最坏情况查询。

固定查询语料应覆盖：一字中文、两字中文、4–8 字中文、长中文、英文单词、英文短语、
中英混合、数字、大小写变体、NFC 等价输入、标点、引号、括号、星号、`OR`/`NEAR` 等
FTS 特殊字符。常见词查询与稀有词查询分别报告。

### 2.3 结构化分布

| 字段 | 分布 |
| --- | --- |
| kind | fact 50%、preference 20%、event 20%、procedure 10% |
| created_by_app | 5 个应用：`desktop-assistant`、`editor`、`browser-helper`、`terminal-agent`、空值各占 20% |
| observed_at | 2024-01-01 至 2026-10-01，均匀分布 |
| updated_at | 2025-01-01 至 2026-10-20，按最近更新倾斜 |
| 状态过滤 | 默认 active；显式 archived；deleted 永不返回 |
| 更新时间过滤 | 最近 7 天、最近 30 天、最近 1 年三组 |

生成器必须写入真实迁移后的表，并通过与生产相同的搜索文档构造器建立 FTS 索引；不能只
向索引表灌数据而绕过业务表。

## 3. 工作负载

| 工作负载 | 请求数/样本 | 并发 | 说明 |
| --- | --- | --- | --- |
| 冷启动搜索 | 200 | 1 | 进程重启并完成数据库打开后立即执行，不做预热 |
| 热搜索 | 20,000 | 4 个读客户端 | 预热 5 分钟后执行，查询语料固定循环 |
| 管理列表 | 2,000 | 1 | 默认 limit=50；含类型/状态/应用过滤组合 |
| 单条读取 | 2,000 | 1 | 随机现有 ID 与不存在 ID 各半 |
| 统一提交持久化 | 2,000 | 1 | 模型关闭/假模型不参与；只测接收事务与 202 返回 |
| 少量并发混合 | 10 分钟 | 4 读 + 1 写 | 读为搜索/列表，写为提交或状态变更，记录错误率 |
| 索引重建 | 3 次 | 1 | 清空派生索引后按规则重建，取中位数 |

搜索查询比例：常见中文 35%、两字中文 20%、英文 20%、混合 15%、稀有词 7%、特殊字符/
标点 3%。每次请求记录端到端 HTTP 延迟、状态码；检索额外记录服务内部耗时。模型调用
不参与上述延迟预算，单独报告。

## 4. 记录与统计

- 预热：正式采样前至少 5 分钟或 2,000 次搜索，二者取较晚完成者。
- 样本：每次请求记录单调时钟耗时；百分位使用最近秩法（nearest-rank），至少保留原始
  CSV/JSON，不只保留汇总值。
- 报告 P50、P95、P99、最大值、吞吐量（requests/second）与错误率。
- 资源：采样间隔 1 秒记录进程 RSS、CPU；数据库、WAL、SHM 与索引体积用 `du`/文件大小；
  重建耗时用进程内计时。
- 报告必须包含硬件、版本、数据种子、命令、并发、预热与原始结果路径。禁止只报告平均值。
- 若未达标，先定位瓶颈，仅优化相关路径后复测；不得事后静默放宽预算。

## 5. 项目验收预算

以下预算适用于上文参考环境和数据分布。**均为项目补充目标，不是原架构 SLA。**

| 指标 | 目标 |
| --- | --- |
| 热搜索 P50 | ≤ 30 ms |
| 热搜索 P95 | ≤ 150 ms |
| 热搜索 P99 | ≤ 300 ms |
| 冷启动搜索 P95 | ≤ 500 ms |
| 管理列表（50 条）P95 | ≤ 50 ms |
| 单条读取 P95 | ≤ 20 ms |
| 提交持久化 P95（不含模型） | ≤ 30 ms |
| 提交持久化 P99（不含模型） | ≤ 100 ms |
| 混合负载错误率 | 0%（预期内的 4xx 除外） |
| 索引重建（100k active + 20k archived） | ≤ 300 s |
| 服务进程 RSS（稳定搜索负载） | ≤ 512 MiB |
| 数据库 + WAL 体积 | ≤ 2 GiB |
| 搜索负载平均 CPU | ≤ 2 个逻辑核 |

模型耗时单独统计，不作为本地搜索预算的一部分；远端超时默认 60 秒、每任务最多三次尝试
的语义由 P5 验证。容量实测、备份恢复和发布准备属于暂缓的 P7，本阶段只固定规格。
